CrossHire Compare · CSV, JSON or a database table, either side · screen by screen

Two tables, every difference, in one page.

Load two tables - a CSV, a JSON file or a database table on either side. Pair their columns in one table - every column from either side is a row, with a dropdown for its counterpart. Set the type once, add transform steps where a side needs them, tick the key, press Compare. Or press Auto and let it work the whole thing out, showing what it does as it goes. Every run leaves one folder with a fixed set of files: the report, the differences as CSV or Parquet, and a JSON with every setting. A second page, Profiling, takes one table on its own and says what a reader wants to know first: which column identifies a row, what stands out, the statistics of every column, its outliers, shapes and dependencies.

This page goes through the app screen by screen. Setting it up, running it locally and the code are in README.md.

python compare_app.pyFastAPI + ReactDuckDB reads the filessix databases, read-onlyDesbordante finds keysone folder per run

02

Sources.

upload, path on disk, or database - one card per side

Each side is a CSV (any delimiter), a JSON file (an array, or one object per line) or a Parquet file. The Profile page's one File card works the same way.

  • Name - shown everywhere and used to name every output file
  • Upload - drop or choose a file; any size, copied to the work folder first
  • Path on disk - read in place, nothing copied, so any size; Browse… opens the file dialog where the app has a screen
  • Folder - with a folder connection saved (section 03), pick a file by its name in that folder instead of a full path
  • Delimiter · First row is a header - for CSV; Advanced takes column names when the header is missing or short
  • Rows to read - a WHERE filter, an order and a top N, applied by DuckDB as the file is read
  • Snapshot the rows read to Parquet - on by default; the rows are read once, then everything reads the snapshot
  • COMPARE_DATA_DIR - when set, a path on disk must sit under one of its folders

Database fetches a table or a query once into a Parquet file in the work folder; from then on the side is a Parquet file like any other.

  • Conn. - pick a saved or environment connection; Manage opens the Connections drawer
  • Password - asked when none is saved, kept for this session only; Change password forgets it
  • A table - schema.table, folded the way the database folds names (hr.employees finds HR.EMPLOYEES on Snowflake)
  • SQL query - one SELECT or WITH statement only
  • Fetch at most - default 1,000,000, 0 = all; a cap with no ORDER BY gets a warning
  • Fetch A · Fetch B - rows stream into Parquet in batches; then Load reads what was fetched
  • Fetch again - the fetch is kept while the connection, SQL and cap stay the same
  • Same SQL as A - on side B, copies A's connection, table or SQL and cap
03

Connections.

named · from a file or the environment · read-only

Connections in the header opens a drawer on both pages. Make or import a connection there, then pick it on a source card.

  • The list - every connection with its name, driver, where it points and where it comes from (env · read-only)
  • Name · Driver - then the fields that driver wants (table below)
  • Password kept - In the file, This session, or Environment variable (only its name is saved)
  • Query timeout, seconds - default 600
  • Test connection - runs the smallest query and says who the database thinks you are
  • Save · Delete · Edit - for connections in your own store; env and shared-file ones are read-only

Many connections in one JSON or YAML file - every driver, folders too.

  • Import a file - in the drawer's Import or export; lists what it holds, then Add N connections saves them
  • Save the passwords written in the file - off by default; a ${NAME} is always kept as written
  • Download mine (.yml, no passwords) - your store as a file to share, secrets left blank
  • COMPARE_CONNECTION_FILES - shared files (;-separated on Windows, : elsewhere), shown read-only

  • A bad record - the whole file is refused, naming the record and what is wrong
Read-only and redacted

Only one SELECT or WITH is ever sent, the session is opened read-only where the driver allows, and every connection is rolled back and closed. Passwords, tokens and keys never reach a report, a log line or the screen; only the DuckDB driver has run against a real database here.

04

The column table.

one row per pair · decide everything in one place

Every column from either side is a row. Pair it, type it, and say what it does in the run.

  • Role - Key, Compare or Skip. Several Key ticks make a compound key; one-sided columns are always Skip.
  • HR column · Payroll column - dropdowns. Pick a partner for a no partner row and the two rows merge.
  • Read as - the type both sides become: number 100.00 = 1e2, date 27/08/2026 = 2026-08-27, boolean 1 = yes = true.
  • Transform - + Add or the steps a side already has; opens the values editor (section 05).
  • Matched by - how the pair was made: name, similarity, guess · check (loose name or values) or you. Guesses are listed under the table.
  • Case - ignore or exact for a text pair; default follows the Ignore case in values switch.
  • The chevron - opens the common name and what each side was detected as and looks like.
  • Summary - the setup card: pairs, key, compare list, how each column is read, suggestions not taken.
  • Match by data - pairs unpaired columns that hold the same values, whatever they are called - Dept with department.
  • Reset to name matches - starts the table over.
  • Save mapping · Load mapping - the pairs, types, roles and steps as JSON, for the next run of the same two feeds.
  • Add a column - a new column from a DuckDB expression on each side, paired like any other.
  • Made as - a preset such as date from a datetime, the hour, month or year, upper, a rounded number, or your own expression.
  • From - picking HR's column picks its partner on Payroll. Leave one side blank and only the other gets it.
  • Checked first - the expression is tried on both files; a typo comes back as DuckDB's own message.
  • dd/mm/yyyy text - presets use TRY_CAST (ISO only); type TRY_STRPTIME("HireDate", '%d/%m/%Y') instead.
One column, two pairs

Split one name into first_name and last_name: pair it twice, each pair with its own part N split by S step.

05

Values: steps, then the type.

per column · per side · previewed on the first rows

Every value goes through the same stages, so both sides compare on the same thing:

01the side's transform steps→02null folding (empty, NULL, N/A, …)→03trim→04the pair's type
  • Open it - click a pair's Transform cell in the column table. Back to the column table returns.
  • HR steps · Payroll steps - one tab per side; each step runs on the result of the one before.
  • Add a step - to the side on screen, or both - HR and Payroll at once (trim, upper, remove spaces).
  • Text steps - trim, upper, lower, left / right N characters, replace text, regex replace, strip leading zeros, digits only, part N split by S…
  • Conversions - to number, to date, to timestamp, to boolean. A conversion sets the pair's type.
  • Custom expression - any DuckDB expression on x, e.g. upper(split_part(x, '-', 1)).
  • Preview on the first rows - before, after the steps, as the type, the other side, and a Match tick.
  • Check this column on all rows - counts the values that do not convert, with examples. Copy to and Clear sit beside the steps.
  • How values are read - null tokens, empty string is null, trim whitespace, ignore case, numeric tolerance.
  • Text parameters - taken as typed: one space is a real separator.
  • Numeric tolerance - only for number pairs; a text 001 against 1 stays a difference.
Example

hired_at is 2026-08-27 10:11:12.123 on A and 27/08/2026 10:11 on B. B: left 10 → to date (%d/%m/%Y) - both compare as 2026-08-27.

06

The key.

on a key · by position · by hash

The top of the Rows page decides how rows pair up. Nothing is measured until you press a button.

  • On a key - rows match on the key columns. Up to four columns can form a key together.
  • By position - line 1 against line 1, for exports that keep their order.
  • By hash of compared columns - pairs rows identical on every compared column, when nothing identifies a row.
  • Add a column - adds a pair to the key; the × on a chip takes it off.
  • Suggest keys - single columns, then pairs, threes, fours - stopping at the first level that finds a key.
  • Each candidate - a chip with its overlap %; the why is under Every figure of the search. Pick one or more, press Use as key.
  • Check key - per side: rows, distinct keys, duplicates and null keys, with a warning when not unique.
  • Speed - over 5,000 rows a 5,000-row sample first; a wide pair with no obvious key takes minutes.
Key written differently - fixed
Case, spaces, leading zeros, a trailing .0: added as steps on each side and said in the Key section.
Key written differently - suggested
A prefix like EMP-, letters and digits only, digits only: nothing changes until you press Apply.
If everything differs

The key is likely spelled differently on each side - e10042 against E10042. Give the key an upper or trim step.

07

Rows.

rows to read · filters · profile on demand

Under the key, the Rows page narrows what is compared. All of it is optional.

  • Rows to read - per side, a DuckDB WHERE, Order by and Top N, applied at load. Build a condition writes one for you.
  • Filters at compare - on the common names, for both sides or one: = != > < in between like is null…
  • Filter values - matched exactly, read as the column's type; a bad date or number is refused in a sentence.
  • Profile by bucket - count a column in every bucket; the Summary then shows which rows match worst.
  • Profile both files - null %, distinct, min and max per column, side by side, plus each side's top and bottom 10 values.
  • Run settings - Re-run on every change, Profile both sides first (with Auto), rows to display per section. Downloads hold every row.
  • Compare HR against Payroll - runs it, with a caption of columns, key and filters.
08

Compare, and what comes back.

a verdict · five tabs · the Log

Press Compare. The running panel lists each step as it goes, and the rail ends on compared in 0.8s.

  • Headline - rows matched on the key, columns compared, rows and cells that differ, one-sided rows
  • Row outcome - one bar: fully matched 2,311 · differ 649 · only in HR 40 · only in Payroll 25
  • Verdict - Identical, Small differences (under 5% of matched rows differ, one-sided rows no more than matched), Differences or Error
  • Summary tab - count tiles, every column with its match bar, the value pairs behind each count
  • Percentages - two decimals, never rounded to 100% or 0% while one row disagrees
  • Stale result - Re-run on every change is off by default; a changed setting marks the result stale
  • Differing rows - one row per key; chips filter by column (department 337, salary 319, active 31)
  • Search - Find a key or value narrows the table; the CSV button downloads every differing cell
  • One-sided rows - a pattern note when the rows share values, then each side with its own CSV
  • Report and Downloads - sections 09 and 10
  • Rows to display per section - caps the tables on screen and in the report; downloads hold every row
  • Log - in the header with its count; each entry has its time, kind and every progress line
  • Auto decisions - one line per decision: pairs, types, steps, the key and why
  • Copy as text, Clear, Close - a running job stays in the Log after Clear
  • Twice at once - starting a job that is already running is refused with That is running already

Auto.

does everything by itself, and logs each decision

Press Auto · figure it all out. Every decision lands in the Log and is a cell or a step you can change.

01
Pair columns
By name, then similar name, then by values - on the sample, department with Dept.
02
Analyse types
Reads the first 50,000 rows a side; adds steps such as remove thousands separators or to date (%d/%m/%Y).
03
Check case
Text that agrees only once case is ignored gets an upper step on both sides.
04
Profile both sides
Only with Profile both sides first ticked (off by default) - minutes on a big pair.
05

Same as Suggest keys, with its reason; nothing unique - the closest; nothing at all - hash mode.

Every paired non-key column, straight away.

12

Run it again from a config.

every run saves its setup · on the page or the command line
  • The file - every run writes <pair>__config.json; Download config and Save config to folder on the Downloads tab
  • What it holds - both sources, the column table with types and steps, key, values switches, filters, formats
  • Never - a password, a token or a private key
  • Run this config - loads both sides, rebuilds the setup and compares
  • Open in the setup instead - goes back to the setup; nothing runs
  • Database side - uses the password typed this session, or asks for it
  • Load mapping - under the column table, reads only the columns part

On the command line - the same comparison on other files, one pair or many:

python -m tablecmp.run HR_compare_Payroll__config.json                       # the config's own two sides
python -m tablecmp.run config.json --left jan/hr.csv --right jan/payroll.csv --out results
python -m tablecmp.run config.json --pairs pairs.csv --out results           # left,right[,name_left,name_right]
  • Names - a side given another file is named after its stem, unless a name is given
  • Folder connection - a bare file name is read in that folder connection; a full path is that file
  • --connections team.yml (-c) - adds a connections file for the run, read-only
  • Output - each pair writes a full run folder under --out
  • Failures - a missing file or column fails its own line; the rest still run
  • Passwords - from COMPARE_PASSWORD_<CONNECTION>, or asked once in a terminal
  • Exit code - 0 all identical, 1 a difference, 2 an error
Not the engine's own config

python csvdiff.py config cannot replay it: the app applies steps, types and key fixes before the engine. tablecmp.run uses the same code as the page.

13

Profiling: one table.

the second page · columns, what stands out, keys, dependencies, one page per column

Pick Profile in the header switch. Load one table, press Profile; Compare keeps its state while you are here.

  • Source card - the same as side A: Name (Table), Upload / Path on disk / Database, Rows to read, Advanced, Load
  • Verdict - Key emp_id - unique on every row · 3,000 rows × 7 columns · 0 duplicate rows · 0 nulls
  • Types - read from the values: 12,686.95 is a number, 06-Nov-2019 a date, Y/N a boolean
  • Progress - the running panel shows each step; the Log gets the run and its Profile notes
  • Big tables - too big to hold in memory, each measure reads the file instead; slower, any size works (see Speed)
  • Bar under the header - Profile; once a profile is on screen, Save to folder and profile.csv too
  • Columns - Column, Type, Nulls, Distinct, Distinct %, Min, Max, Top value
  • Distinct % - one bar for all rows; a second, non-null, when the column has nulls
  • Top value - the most frequent value with its bar, e.g. department Support 13.73%
  • Open a column - click its name for the column's own page
  • Below - What stands out, Could be another type (when any column could), Key candidates, the Outliers, Patterns and Dependencies tables, then Value frequencies and Files
  • One line per finding - the columns it covers beside it, e.g. Nearly unique · salary 5 rows
  • Kinds - empty or constant columns, many nulls, outliers, negative values, dates after today, stray spaces, case variants, leading zeros
  • Left out - what the page shows elsewhere: the key, a column's values, the type it was read as
  • Full notes - one per line in the Log and in notes.txt
  • Columns in a key, up to - 1 to 6, 5 by default
  • Checked on every row - the best 5, 10 or 20 sample hits are counted on the whole table
  • Candidates listed - 3, 5, 10 or 20; the choices are sent with the next Profile
  • Search - single columns first, then combinations on a 100,000-row random sample; each key found is minimal
  • Each card - distinct, duplicates and null keys, each as a count, a bar and a %, then the reasons
  • Sample - emp_id unique by itself; first_name + last_name + hire_date unique together; the next three repeat on 3, 4 and 8 rows
  • Never a key - a combination with a null, or a checksum column such as row_hash
  • Cell - how far the row's column decides the column above it beyond chance, in %: 0 unrelated, 100 one value each
  • Shading - from 30% up, darker the higher
  • Rows - only columns with no more distinct values than half the rows; others decide everything by size alone
  • Then - when any exist, a graph and the functional dependencies (X → Y, many-to-one or one-to-one); correlated pairs with |r| ≥ 0.7
  • Payroll - Dept → CostCenter, many-to-one with 11 distinct values
  • Navigate - All columns back, Previous / Next to the neighbouring columns
  • Stat cards - Rows, Nulls, Distinct, Min, Q1, Median, Mean, Q3, Max, Std dev, Top value
  • Length cards - Min, Avg and Max length in characters, of the value as read
  • Distribution - number, date and timestamp columns: 10 equal bins, rows per bin, a line on its shape
  • Could be read as - a text or number column whose values would read as a number, a date or a timestamp: how many, the type (DECIMAL(p, s), BIGINT, TIMESTAMP) and the format, e.g. %Y%m%d%H%M%S for 20260504004217
  • Parts - a number by its digits before and after the point in bands (1-3, 4-6 …), a date by year, month and weekday (and hour), text by its most common first and last 1 to 5 characters
  • Outside the fence - count and %, and which side: low, high or both; none on salary
  • No fence - whole numbers that are nearly all different or 9+ digits long read as a code, and digits that read as a date or timestamp say so; a spread means nothing for either
  • Fence - Q1 − 1.5 × IQR … Q3 + 1.5 × IQR, with Q1, Q3 and IQR written out; P1 to P99 below
  • Lowest … highest - flagged when the highest is 10× the P99 or more: check for a unit or entry error
  • Zero · negative - counts and %; 5% zeros or more is flagged, a zero can stand for a missing value
  • Shapes - spelled out, e.g. 2 letters · 6 digits · 2 letters · 15 digits; a number shows digits before the point, places after and the DECIMAL(p, s) it fits
  • One decimal - not a problem: a trailing zero dropped on export (10.10 → 10.1)
  • Most and least frequent - ten each; 11 to 20 values list the rest once; 10 or fewer show every value once
  • Dependencies - the 5 it decides most and the 5 that decide it most, each a bar; under 30% faint, not conclusive

Speed.

nothing heavy runs unless you press it
  • Load - sniffs the schema from a sample, one pass to snapshot and count; previews stop at 10 rows.
  • On a button only - key search, profile, type check and the comparison; Auto runs them once and reuses its profile.
  • Key search - can take minutes on a wide table; over 5,000 rows each level is tried on a 5,000-row sample first.
  • Databases - fetched once in 50,000-row batches into Parquet; put the WHERE in the SQL, ORDER BY with a cap.
  • Memory - DuckDB gets 2 GB and spills up to 20 GB to disk; change both under Run settings.
  • Big files - cut them in Rows to read first (a date filter or a top N) and keep the Parquet snapshot on.
  • Rough timings - the sample pair in about a second; 500,000 × 6 in 16 s for a whole Auto run; 100,000 × 200 in 57 s.
